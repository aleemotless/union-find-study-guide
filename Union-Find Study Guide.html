Topic overview

What this video teaches

Union-Find manages a collection of disjoint sets: groups that never share an element. It supports two questions fast: which group does an element belong to, and can we merge two groups into one. The video builds the structure in four versions, each fixing a weakness of the previous one.

It matters because many graph algorithms reduce to these two questions. The video names three uses: detecting whether a graph has a cycle, finding which nodes in a network are connected, and building a minimum spanning tree with Kruskal's algorithm (the subject of the next video).

Part 1 · Foundations

The three operations

Every Union-Find exposes three operations. The video explains them through a company where every employee reports to a direct manager.

OperationWhat it doesCompany analogy
make_set(x)Puts each element in its own group; the element is its own parent.A new employee joins and, at first, reports only to themselves.
find(x)Returns the root (representative) of x's group. The root is the group's identity.Follow your manager, then theirs, until you reach someone who reports to no one else: the top boss.
union(x, y)Merges the groups of x and y, if they are not already the same group.A reorganization: two departments merge, and one of the two top bosses becomes boss of everyone.
The key test

Two elements are in the same group exactly when find(a) == find(b). Two employees who reach the same top boss work in the same department.

Part 2 · Foundations

Trees stored in a single array

We draw Union-Find as trees, but code stores it as one array called parent. The index is the element; the value is that element's parent.

  • Following parent links upward always ends at the root, the unique representative of the group.
  • The array form is simple, fast, and memory-efficient: one integer per element.
  • Elements that are not integers (for example strings) are no problem: use a hash map to assign each one a unique index, then run Union-Find on the indices.

Part 4 · Build it

Version 1.0, and why it slows down

The basic implementation maps directly onto the three operations. Its weakness: nothing controls how tall the trees grow.

# Union-Find v1.0 (from the video)
class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))      # make_set: parent[i] = i

    def find(self, x):
        while self.parent[x] != x:        # climb until a node is its own parent
            x = self.parent[x]
        return x                          # that node is the root

    def union(self, x, y):
        root_x = self.find(x)
        root_y = self.find(y)
        if root_x != root_y:              # already in the same set? do nothing
            self.parent[root_y] = root_x  # root_y now points to root_x

The worst case: a chain

If unions keep hanging trees in the wrong place, the forest stretches into one long chain. Then find(7) must walk every link: 7 → 6 → 5 → … → 0.

Precision note

The video describes the chain as coming from union(0,1), union(1,2), …, union(6,7). With the v1.0 code above, which links root to root, that exact order produces a flat star under 0. The chain 7 → 6 → … → 0 appears when the same unions arrive in reverse order: union(6,7), union(5,6), …, union(0,1). The lesson is unchanged: v1.0 has no rule to keep height low, so some input order will always build a chain.

Part 5 · Fix #1

Union by rank and union by size

The fix: when merging, attach the smaller tree under the larger one. The root of the big tree stays the root, so most nodes do not get deeper. There are two ways to measure "smaller".

Union by rank (v2.0)Union by size (v2.1)
TracksHeight of each tree, in a rank arrayNumber of elements, in a size array
Merge ruleLower-rank root points to higher-rank rootSmaller-size root points to larger-size root
TiePick either root; its rank grows by 1Pick either; add the sizes
GoalSame for both: keep trees flat so find stays fast
StrategyComparesResult
Union by rankrank 2 vs 1Shorter tree B goes under A: parent[4] = 0
Union by sizesize 4 vs 5Smaller tree A goes under B: parent[0] = 4
Beyond the video

Either rule alone guarantees a tree height of at most about log₂ n, so find becomes O(log n) instead of O(n). In the example, union by size makes the merged tree one level taller than union by rank would, yet the logarithmic guarantee still holds for both.

Part 6 · Fix #2

Path compression

Balanced unions keep trees short. Path compression goes further: every time find climbs to the root, it makes each node it passed point directly at the root.

Version 3.0 adds this on top of union by rank. Only find changes: it becomes recursive, and on the way back from the root it overwrites each node's parent with the root.

Common misconception

Path compression changes tree heights but does not update rank. After compression, rank is an upper bound on height, not the exact height. That is fine: the algorithm only needs rank to compare trees, and the complexity proof relies on this bound. (beyond the video)

Adds a rank array (tree height). Lower rank goes under higher rank.

class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))
        self.rank = [0] * n               # every single-node tree has height 0
    def find(self, x):
        while self.parent[x] != x:
            x = self.parent[x]
        return x

    def union(self, x, y):
        root_x, root_y = self.find(x), self.find(y)
        if root_x == root_y:
            return
        if self.rank[root_x] < self.rank[root_y]:
            self.parent[root_x] = root_y  # shorter tree under taller
        elif self.rank[root_x] > self.rank[root_y]:
            self.parent[root_y] = root_x
        else:                             # equal heights: either way,
            self.parent[root_y] = root_x
            self.rank[root_x] += 1        # and the new root grows by 1

Replaces rank with size (element count). Smaller tree goes under larger.

class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))
        self.size = [1] * n               # every tree starts with 1 element
    def find(self, x):
        while self.parent[x] != x:
            x = self.parent[x]
        return x

    def union(self, x, y):
        root_x, root_y = self.find(x), self.find(y)
        if root_x == root_y:
            return
        if self.size[root_x] < self.size[root_y]:
            root_x, root_y = root_y, root_x   # make root_x the bigger tree
        self.parent[root_y] = root_x
        self.size[root_x] += self.size[root_y]

v2.0 plus path compression. Only find changes. Each operation: O(α(n)).

class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))
        self.rank = [0] * n

    def find(self, x):
        if self.parent[x] != x:                       # not the root yet:
            self.parent[x] = self.find(self.parent[x]) # find root, then point x at it
        return self.parent[x]

    def union(self, x, y):
        root_x, root_y = self.find(x), self.find(y)
        if root_x == root_y:
            return
        if self.rank[root_x] < self.rank[root_y]:
            self.parent[root_x] = root_y
        elif self.rank[root_x] > self.rank[root_y]:
            self.parent[root_y] = root_x
        else:
            self.parent[root_y] = root_x
            self.rank[root_x] += 1

Beyond the video: the same v3.0 in Java. find is iterative (two passes) so a deep tree cannot overflow the call stack on the first call, and union returns false when x and y were already connected, which is the hook for cycle detection and Kruskal's algorithm.

public final class UnionFind {
    private final int[] parent;
    private final int[] rank;

    public UnionFind(int n) {
        parent = new int[n];
        rank = new int[n];
        for (int i = 0; i < n; i++) parent[i] = i;      // make_set
    }

    public int find(int x) {
        int root = x;
        while (parent[root] != root) root = parent[root]; // pass 1: locate the root
        while (parent[x] != root) {                        // pass 2: compress the path
            int next = parent[x];
            parent[x] = root;
            x = next;
        }
        return root;
    }

    /** @return false if x and y were already in the same set (an edge x–y would close a cycle) */
    public boolean union(int x, int y) {
        int rx = find(x), ry = find(y);
        if (rx == ry) return false;
        if (rank[rx] < rank[ry]) { int t = rx; rx = ry; ry = t; } // rx = taller tree
        parent[ry] = rx;
        if (rank[rx] == rank[ry]) rank[rx]++;
        return true;
    }

    public boolean connected(int x, int y) { return find(x) == find(y); }
}
Part 7 · Result

Performance: the inverse Ackermann function

Combining union by rank with path compression makes each operation cost O(α(n)), where α is the inverse Ackermann function. It is not strictly constant, but it grows so slowly that, as the video puts it, α(n) is at most 4 or 5 for any practical input size. Treat it as constant.

VersionExtra stateUnion rulefindWorst case per op
v1.0noneroot_y → root_xloopO(n)
v2.0rank[]lower rank → higherloopO(log n) †
v2.1size[]smaller → largerloopO(log n) †
v3.0rank[]lower rank → higherrecursive + compressO(α(n))

† Standard result, not stated in the video. Memory is O(n) for every version: one or two integer arrays.

  • Cause and effect: find's cost equals the depth of the node, so every optimization is really a way to control depth.
  • The two fixes are complementary. Union by rank/size prevents tall trees from forming; path compression repairs whatever depth remains, and does it as a side effect of work you were doing anyway.
  • Union depends on find. Union calls find on both arguments, so a faster find speeds up union too.
Quick revision sheet

The whole video on one screen

What it is

A structure for disjoint sets: test whether two elements share a set, and merge two sets.

How it's stored

parent[i] is i's parent. A root has parent[r] == r. Map strings to indices with a hash map.

find(x)

Follow parents to the root. Same root means same set.

union(x, y)

Find both roots; if they differ, make one root the parent of the other.

The flaw in v1.0

Trees can become chains, so find is O(n).

Union by rank / size

Attach the shorter (rank) or smaller (size) tree under the other.

Path compression

During find, point every visited node directly at the root.

Final cost

Rank + compression: O(α(n)) per operation, effectively constant.

Key terms

Disjoint sets
Sets with no element in common; each element is in exactly one set.
DSU
Disjoint Set Union, another name for Union-Find.
Root / representative
The element that is its own parent; it identifies its whole set.
Parent array
Array where index = element and value = that element's parent.
Forest
A collection of rooted trees, one per set.
Rank
Per-root number tracking tree height, used by union by rank.
Size
Per-root count of elements, used by union by size.
Path compression
Rewriting parent links during find so visited nodes point straight at the root.
α(n)
Inverse Ackermann function; at most 4 or 5 for practical n.
Dynamic connectivity
Answering connectivity queries while connections keep being added.

Knowledge check

Test yourself

Answer each on paper first. Answers are in the next section.

  1. Start from parent = [0,1,2,3,4,5,6,7]. Using v1.0, run union(0,1), union(2,3), union(0,2). Write the parent array, and list the nodes find(3) visits.
  2. Why does v1.0's find degrade to O(n), and why does that also slow down union?
  3. Tree A (root 0) has height 2 and 4 elements. Tree B (root 4) has height 1 and 5 elements. Which root becomes the parent under union by rank, and which under union by size?
  4. A chain 3 → 2 → 1 → 0 exists. Describe the parent array after one call to find(3) in v3.0.
  5. The final version is described as "nearly constant time". What is the exact bound, and why is it fine to treat it as constant?
Answers

Check your work

1. Parent array after three unions

parent = [0, 0, 0, 2, 4, 5, 6, 7]. find(3) visits 3, then 2, then 0, and returns 0 because parent[0] == 0. Note that parent[3] stays 2: union only re-parents roots.

2. Why v1.0 degrades

v1.0 links roots with no regard to height, so some sequences of unions build a chain of n nodes. find walks one link per level, so it costs O(n). Union calls find on both arguments before linking, so it inherits the same cost.

3. Rank vs size

By rank, B (rank 1) goes under A (rank 2): parent[4] = 0, root 0. By size, A (4 elements) goes under B (5 elements): parent[0] = 4, root 4. The heuristics measure different things, so they can choose differently.

4. Path compression on a chain

Every node on the path is rewritten to point at the root: parent[1] = 0, parent[2] = 0, parent[3] = 0. The chain becomes a star, and later finds on 1, 2 or 3 take one hop.

5. The α(n) bound

With union by rank and path compression, each operation is O(α(n)), where α is the inverse Ackermann function. It grows so slowly that it is at most 4 or 5 for any input size you could store, so in practice it behaves like a small constant.
